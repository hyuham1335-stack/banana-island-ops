## 서술

### 문제

사용자 요청 "must 다음 작업 확인 후 진행해줘"에 따라 Must 진행 상황을 조사한 결과, FR-004(제목+앵글 생성)까지 구현됐고 PR #7 이 열려 있었으나 07-pr-review(내장 코드리뷰)가 남긴 미해결 Major 3건 — G-1(프롬프트 인젝션 구분자 이스케이프 누락) · G-2(예산 타이머가 resolveRules 지연을 놓침) · G-3(JSON 복구 정규식의 탐욕적 매치) — 이 PR 코멘트로만 남아 있었다. 08-report(런 20260914-2058-0053)가 "머지 전에 별도 수리 런으로 처리"를 권고했다.

### 원인

다음 Must 항목(FR-005)이 이번에 고칠 세 파일(prompts.ts·content-generation.ts·client.ts)을 그대로 재사용하므로, 결함을 안은 채 새 기능을 쌓으면 결함이 전파된다고 판단해 사용자에게 확인 후 이 수리를 먼저 진행하기로 했다.

### 해결

01-plan 이 3라운드에 걸쳐 수렴했다 — 내부 plan-reviewer 가 1라운드에 Major 1건(재현 테스트 지연값 산수 오류)·Minor 1건(topicMemo 미검증)을 잡았고, 02-cross-verify(Gemini)가 낸 Critical(고정 INITIAL_TIMEOUT_MS 가 예산 타이머 이동과 맞물려 502 위험)이 플랜을 01 로 되돌렸다. 그 수정 자체에 새 경계값 결함(음수 timeoutMs)이 있어 02 가 왕복 한도(1회)를 넘겨 두 번째 Critical 을 냈고, 사용자가 에스컬레이션에서 '이대로 진행한다'를 확정해(이미 하한 가드가 반영된 상태) 진행했다. 03 에서 impl·test 역할을 병렬 실행했고(계약: 유닛 3개), test 역할이 작성한 client.test.ts 의 Anthropic 목이 화살표 함수라 `new` 생성자 호출이 안 되는 버그를 로컬 테스트 실행으로 발견해 test 역할에게 되돌려 고쳤다. 04 게이트(전체 회귀 241개)·05-code-review(gen·data, Major 0·Minor 1)를 통과했고, 05→06 사이에 커밋(f6ac9e4)한 뒤 사용자 승인을 받아 push 하고 기존 PR #7 을 갱신했다(신규 생성이 아님 — 파이프라인 state 는 PR 을 몰랐으나 실제로는 이미 존재해 update 로 처리). 07 은 05 가 깨끗해(ok·Major 0·04/05 수리 없음) 내장 리뷰를 생략했다(ADR-H043). 승격 스캔 후보 0건.

### 배운 점

"타이머 시작점만 옮긴다"처럼 좁게 정의한 수정도, 그 수정이 실제로 막으려는 실패 모드(구조화된 에러 없는 강제 종료)를 완전히 닫으려면 인접한 상수(고정 INITIAL_TIMEOUT_MS)까지 같이 봐야 한다는 것을 02-cross-verify 가 두 차례에 걸쳐 보여줬다. 또한 02 의 왕복 한도(1회)를 넘긴 뒤에도 외부 리뷰어(Gemini)는 계속 새 지적(10ms 타임아웃 낭비, 코드펜스 폴백 서술의 자기모순, 디코드-후-재인코딩 제안)을 냈는데, 그중 일부(디코드 제안)는 오히려 안티패턴이었다 — 외부 리뷰의 모든 지적을 기계적으로 수용하지 않고 각각을 최소 예산·기존 테스트와의 정합성 기준으로 accept/reject 하는 것이 왕복을 무한히 열지 않으면서도 정직하게 처리하는 방법이었다.
