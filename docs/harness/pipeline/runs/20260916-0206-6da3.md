## 서술

### 문제

approved 상태 콘텐츠를 채널(인스타/아마존/블로그)별 발행 형식으로 변환해 보여줄 방법이 없어 담당자가 발행 준비 단계에서 수작업으로 형식을 맞춰야 했다(FR-012, PRD US-012).

### 원인

채널 형식 변환 로직 자체가 아직 구현되지 않았다 — 이전 런들(FR-009~011)은 검수/승인 흐름까지만 다뤘고, 발행 직전 단계(FR-012~014)는 손대지 않은 채 남아 있었다.

### 해결

lib/channel-format.ts에 순수 함수 formatForChannel을 새로 만들고(linkPolicy 3분기: bio=해시태그 추출+본문 그대로, none=본문 그대로, inline=UTM 링크 없으면 본문 끝에 추가), services/content-workflow.ts에 resolveChannelFormat을 추가해 approved 상태에서만 채널 조회 후 계산하도록 getContentDetail·approveContent를 확장했다. ContentDetail.channelFormat 필드 추가에 맞춰 UI(ChannelFormatCard.tsx, 복사·글쓰기 열기 버튼)도 연결했다.

### 결과

PR #14(feat-fr-012-channel-format → main) 생성, 04 게이트(150개 테스트)·05 코드리뷰(gen/data/sec/arch 4명, 1차 지적 3건 모두 정리)·07 내장 코드리뷰(effort=low) 통과. 완료 등급 PASS_WITH_GAPS. 머지는 하지 않았다.

### 배운 점

1) 01-plan 단계에서 작성한 계약이 resolveChannelFormat 시그니처에 body 필드를 빠뜨려 02-cross-verify에서 critical로 되돌아왔다 — 계약 작성 시 두 함수(formatForChannel↔resolveChannelFormat) 간 데이터 전달 경로를 시그니처 수준까지 맞춰봤어야 했다. 2) 새 필드를 기존 함수(toContentDetail)의 필수 반환값에 추가하면 그 함수를 호출하는 모든 기존 골든/라우트 테스트가 영향받는다는 것을 계약 작성 시 과소평가해 8개 파일 중 1개(content-generation.test.ts)를 잘못 포함시켰다가 05에서 오탐으로 재확인하는 왕복이 생겼다. 3) resolveContentLink·resolveChannelFormat의 salesChannels 중복 SELECT는 계약 설계 단계에서 놓쳤고 05 data 리뷰어가 잡아냈다 — 파생 조회 함수를 새로 추가할 때 기존 조회 함수와 같은 테이블을 다시 긁는지 먼저 확인했어야 했다.

### 계약이 어디서 부족했는가

resolveChannelFormat 시그니처에 formatForChannel이 요구하는 body를 처음에 빠뜨렸다(02-xv critical → 계약 수정). channelFormat 필드 추가가 파급되는 기존 테스트 파일 범위를 부정확하게 특정했다(8개 중 content-generation.test.ts 1개는 실제로 영향 없었음 — 05 gen 리뷰어가 critical로 재확인해 오탐으로 확정). resolveContentLink/resolveChannelFormat의 salesChannels 중복 SELECT를 계약 설계 시 놓쳤다 — 05 data 리뷰어가 CONTRACT_DEFECT로 잡아 MVP 범위 트레이드오프로 계약에 명시했다(공개 시그니처 변경 파급이 이번 범위보다 크다는 이유).

### 05 리뷰 범위가 적절했는가

05는 4명(gen·data·sec·arch) fanout으로 적절했다 — 실제 로직 결함(sec: approveContent의 try/catch 누락)과 설계 트레이드오프(data: 중복 조회)를 정확히 구분해 잡았고, gen의 critical 지적은 직접 파일을 읽어 확인한 결과 오탐이었다(델타 재리뷰로 해소). arch는 지적 0건. 07의 내장 코드리뷰(effort=low, 04·05 수리가 있었기 때문)는 추가로 minor 3건(채널 형식 카드의 빈 링크 복사 버튼, 해시태그 정규식의 구두점 포함, 데이터 흐름 설계 재확인)을 찾았고 05 data의 지적을 정확히 재식별(reraised_from_previous)했다 — 리뷰 범위가 05→07로 이어지며 일관되게 작동했다.
