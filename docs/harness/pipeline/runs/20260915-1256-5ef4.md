### 배운 점

'system 프롬프트를 공유한다'는 요구를 코드 재사용(같은 함수 호출)으로 만족시키려 하면, 그 함수가 호출부마다 달라야 하는 부분(출력 형식)까지 하드코딩돼 있을 때 실제 동작이 깨질 수 있다 — 함수 시그니처 재사용과 '의미상 같은 system'은 다른 주장이고, 플랜·계약·리뷰 전부가 전자만 확인하고 후자(실제 문자열이 응답 스키마와 정합적인가)는 아무도 실행 경로를 끝까지 따라가며 검증하지 않았다. LLM 프롬프트를 다루는 함수는 유닛 테스트가 '회귀 없음'을 확인하는 것만으로는 부족하고, 최소한 그 프롬프트가 지시하는 출력 형식과 실제로 파싱에 쓰는 zod 스키마가 일치하는지를 명시적으로 assert하는 테스트가 있어야 한다(이번 런에서 사후 추가함).

### 계약이 어디서 부족했는가

계약 §2.4(§유닛 buildBodySystemPrompt 관련부)가 '별도 함수를 만들지 않고 buildTitlesSystemPrompt를 examples 인자로 확장해 재사용한다'고 명시했는데, 이것이 정확히 07에서 발견된 결함의 근원이다 — 계약 자체가 틀린 설계를 확정해 구현(impl)은 계약을 정확히 따랐음에도 버그가 났다. 또한 계약은 drizzle-kit generate 산출 SQL에 DEFAULT 명시를 요구하지 않았다 — 빈 테이블 확인이라는 절차적 완화만 있고 마이그레이션 파일 자체의 방어성은 다루지 않았다(이번 런은 이 갭을 고치지 않고 다음 배포자의 재확인 절차로 남겼다).

### 05 리뷰 범위가 적절했는가

05는 gen·data·sec·arch 4명이 모두 돌았고 major 1건(INTERNAL 미검증)을 정확히 잡았지만, 4명 모두 system 프롬프트 문자열의 실제 출력 형식 지시와 응답 zod 스키마를 교차 대조하지 않았다 — 계약이 이미 '재사용'을 명시했기 때문에 계약 대조만으로는 이 결함이 드러나지 않는 구조였다. 07의 /code-review(effort low)가 이것을 처음 잡았다(escaped_05 1건, critical). 05 라우팅 자체의 문제라기보다, 프롬프트/스키마 짝을 기계적으로 대조하는 검사(예: 05 contract-trace 확장)가 없었다는 것이 더 근본적인 갭으로 보인다.
