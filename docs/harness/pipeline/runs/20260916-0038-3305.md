## 서술

### 문제

사용자가 '/feature must 다음 작업 확인 후 진행해줘'로 다음 Must 작업을 스스로 찾아 진행하라고 요청했다. 요청 원문에 구체적 범위가 없어 00-triage가 unclear로 판정, 사람이 profile=normal을 확정했다.

### 원인

동일 요청 원문으로 진행된 직전 런(20260915-2042-728c)이 FR-010(승인)·FR-011(반려)의 백엔드(PR #12)를 이미 구현·머지했지만, 프론트엔드에는 승인/반려 UI가 전혀 없었다. 추가로 role 쿠키를 설정하는 코드가 프로젝트 어디에도 없어 admin 역할로 전환할 방법 자체가 없었고(그러면 승인/반려 버튼을 화면에서 절대 볼 수 없다), 검수함(Inbox) 진입점도 없었다 — 셋이 서로의 전제조건이라 한 런으로 묶었다.

### 해결

Plan 모드에서 Explore 서브에이전트 2개로 PRD·코드 상태를 조사하고 Plan 에이전트로 설계를 잡은 뒤 사용자 확인을 받아 계획을 승인받았다. 하네스 파이프라인으로 전환해 01-plan을 다시 작성(plan-reviewer 1라운드, major 2건: /api/role이 process.env 직접 읽음, ContentActions 승인 후 렌더 분기 누락 — 둘 다 계약에 반영). 02-cross-verify(mcp__plan-review__review_plan, 1회 503 재시도 후 성공)가 critical 1건을 냈으나 설계 결정 표에 이미 router.refresh() 호출이 명시돼 있음을 직접 대조로 확인해 기각했고, 나머지 major 2건(멀티탭 미동기화·프로덕션 인가 없음)·minor 2건도 기존 코드베이스의 동일한 특성이거나 PRD가 이미 합의한 설계임을 근거로 기각했다. 03에서 계약을 메인이 직접 쓰고 impl-writer·test-writer를 병렬 실행, 둘 다 status:ok로 완료. 04-gate 통과. 05-code-review에서 precheck가 예산 초과(19파일>10)와 브랜치(main) 결정을 요구해 사용자가 각각 '그대로 진행'·'feat-fr-010-011-frontend'를 선택했다. contract-trace는 major 10건(그중 9건은 컴포넌트 테스트 인프라 부재로 계약이 의도적으로 제외한 것, 1건은 maxDuration export가 계약 표기 방식상 못 잡힌 것)을 냈으나 critical 0건. 리뷰어 4명(gen·arch·data·sec) 전원 findings 0건.

### 결과

PR #13(feat-fr-010-011-frontend → main)을 생성했다. 06 승인은 사용자가 push+pr 범위로 명시 승인했다. 07은 외부 리뷰 봇이 꺼져 있고(disabled) 05가 깨끗해 내장 /code-review를 생략했다(ADR-H043, clean_05). 승격 후보 2건(maxDuration NAMING 3런 연속, 컴포넌트 미테스트 TEST_MISSING_FAILURE_PATH 2런)은 둘 다 근거를 들어 skip 판정했다. 완료 등급 PASS_WITH_GAPS(stage_absent:e2e·docs, adapter_unverified — 이 스택에 원래 없는 것들, 이번 작업과 무관).

### 배운 점

타이트하게 결합된 UI 작업(역할 전환 없이는 승인/반려 버튼에 도달 불가)은 05 예산(파일 10개)을 구조적으로 넘기 쉽다 — 분리하면 각 조각이 개별적으로 데모·테스트 불가능해진다는 점을 사용자에게 명시해 판단을 받았다. contract-trace의 out_of_contract 검사는 camelCase Next.js 라우트 설정 export(maxDuration)를 계약 심볼로 못 세는 게 설계 의도인데, 이게 매 API 라우트마다 반복 발생해(이번이 3런째) 승격 후보로 뜬다 — 실제 결함이 아니라 도구 한계이므로 lint 규칙화는 부적절하다고 판단해 기각했다. mcp__plan-review__review_plan(Gemini)이 일시적 503을 낼 수 있어 한 번의 재시도가 필요했다.

### 계약이 어디서 부족했는가

계약은 01_plan.md와 그 리뷰(01 내부 plan-reviewer·02 xv)에서 나온 채택 보정(F-1: /api/role이 getEnv() 경유하도록 env.ts에 NODE_ENV 필드 추가, F-2: ContentActions의 승인 후 렌더 분기를 세 갈래로 명시)을 전부 반영한 채로 작성했다 — 03 구현자들에게 넘어갈 때 모호함이 없었다. contract-trace가 낸 10건의 major는 계약이 이미 '계약 밖(에이전트 자율)' 절에서 컴포넌트 테스트 인프라 부재를 명시적으로 배제한 결과이거나(9건) 계약의 백틱 표기 관례가 camelCase export를 못 세는 도구 한계(1건)이고, 실제 계약-구현 불일치는 아니다.
