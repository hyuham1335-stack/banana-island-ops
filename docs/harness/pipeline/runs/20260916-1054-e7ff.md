## 서술

### 문제

요청 원문("must 다음 작업 확인 후 진행해줘")이 구체적 범위를 지정하지 않아, PRD의 Must 순서(FR-001~006→FR-009~013→FR-007·008·014)와 코드 조사로 FR-013(발행 완료 기록, approved→published)이 다음 작업임을 확정하고 구현했다.

### 원인

FR-013의 URL 도달성 확인(lib/url-check.ts)이 사용자 입력 URL을 서버에서 fetch하는 SSRF 표면이라, 계약 초안의 방어(단순 사설 IP 문자열 매칭)로는 부족했다. 02 교차검증(Gemini)과 05 코드리뷰(4관점 fanout, 그중 sec)가 라운드를 거듭하며 redirect 추종, IPv6 대괄호 표기, fe80::/10 범위 계산 오류, 0.0.0.0/:: 미지정 주소, DNS 리바인딩(TOCTOU)을 순차로 찾아냈다.

### 해결

redirect:"error", IPv6 대괄호 벗기기, fe80 범위 계산, 0.0.0.0/:: 차단, fetch 전 dns.lookup 사전조회를 추가했다. 05 review_repair 예산(2회)을 다 쓴 뒤에도 sec가 DNS 리바인딩의 잔여 TOCTOU 창을 critical로 재상정했고, 사용자가 에스컬레이션에서 '미해결 지적을 안고 진행'을 선택해 완전한 IP 고정(pinning) 방어는 다음 과제로 남겼다. 07 내장 코드리뷰(medium)가 추가로 찾은 발행 결과 알림 소실·dns.lookup 무제한 대기·URL 스킴 미제한 3건은 그 자리에서 직접 고쳐 push했다.

### 결과

PR #15(feat-fr-013-publish→main) 생성, 전체 회귀 551개 테스트 통과, 등급 PASS_WITH_GAPS. 남은 위험(DNS 리바인딩 TOCTOU)은 계약 문서와 PR 본문에 알려진 한계로 명시했고 코드는 병합되지 않은 채 사람의 리뷰를 기다린다.

### 배운 점

00-triage에 넘길 요청이 너무 짧아 프로파일을 기계가 못 정하면(unclear), '다음 작업이 무엇인지'까지 사람이 대신 조사해 확정해야 한다 — 이번에는 플랜 모드로 그 조사를 먼저 마친 뒤 파이프라인에 넣었다. 또한 05의 review_repair 예산(2회)은 SSRF처럼 라운드마다 새 공격 표면이 드러나는 보안 이슈에는 부족할 수 있어, 예산 소진 후에도 사람이 '진행'을 택하면 이후 라운드(3라운드 이상)의 리뷰어 accounting 규약(reraised_from_previous가 가리켜야 할 id가 라운드를 넘어가며 바뀌는 것)을 메인이 정확히 안내해야 한다는 것을 실수로 배웠다(gen 3라운드 제출을 한 번 잘못 안내해 재작업했다).

### 계약이 어디서 부족했는가

계약이 「외부 경계」 절에 HEAD fetch 하나만 적었을 때는 SSRF 방어가 전혀 없었다 — 02·05 라운드를 거치며 redirect 정책, IPv6 표기, DNS 리바인딩을 하나씩 추가해야 했다. 처음부터 '사용자 입력 URL을 서버에서 fetch한다'는 문장이 있었다면 SSRF 체크리스트를 계약 단계에서 한 번에 반영할 수 있었을 것이다. DNS 리바인딩의 완전한 방어(IP 고정)는 계약에 여전히 미해결로 남아 있다.

### 05 리뷰 범위가 적절했는가

05는 gen/data/sec/arch 4관점 fanout으로 소스 변경 전체를 봤고 test는 예산 상한으로 빠졌다(보고서에 그대로 남긴다). sec 혼자 SSRF 표면 전체를 세 라운드에 걸쳐 찾아냈고 gen도 독립적으로 같은 IPv6 결함을 찾아 합치가 있었다 — 리뷰 범위 자체는 적절했다. 다만 review_repair 예산(2회)이 소진된 뒤 3라운드째 sec의 accounting이 두 번 형식 위반으로 튕겨 결국 failed로 닫혔다 — 실질적으로는 3라운드에서 sec가 0.0.0.0 이슈를 resolved로, DNS 리바인딩을 critical로 재상정한 내용 자체는 유효했지만 원장에는 '실패'로만 남는다(review05:degraded gap).
