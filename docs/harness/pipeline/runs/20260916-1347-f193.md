## 서술

### 문제

### 원인

구현 자체보다 두 가지 판단이 필요했다. (1) Must 중 다음 작업이 FR-007/008/014/016 중 무엇인지 사용자에게 확인이 필요했고(FR-016 선택됨), (2) 01-plan 완성본을 02-cross-verify(xv)가 검토하며 채널별 광고 성과를 editor 역할도 그대로 조회할 수 있는 설계였음을 critical로 지적했다 — CLAUDE.md의 '광고 데이터 조회는 서버가 역할을 검사한다'는 CRITICAL 규칙 위반이었다.

### 해결

xv의 critical을 반영해 getHomeDashboard(deps, actor)가 admin일 때만 광고 조인 쿼리를 실행하고 editor면 adSummary:null을 서버에서 강제하도록 설계를 바꿨다(01-plan 2라운드에서 재수렴, xv 재검증 통과). 04-gate에서는 테스트 실패 1건이 나왔는데, impl이 직접 원인을 추적해 '구현이 아니라 테스트 더블의 getter destructuring 타이밍 버그'임을 밝혀냈고, 사다리 규칙대로 test 역할로 재배정되어 올바르게 수리됐다. 05-code-review에서는 test-quality 리뷰어가 '필터 조건 값 자체를 검증하지 않아 로직이 뒤바뀌어도 테스트가 통과한다'는 major를 지적했고, 수리 후 mutation testing(로직을 실제로 되돌려 빨간불 확인)으로 해소를 검증했다.

계약은 Table 컴포넌트가 ContentSummary/AdChannelSummary 두 데이터 모양을 어떻게 구분해 렌더링하는지(headers/renderRow를 호출부가 넘기는 제네릭 설계)까지 구체적으로 못박아 뒀다 — 01-plan 2라운드 리뷰가 '두 모양 구분 설계가 없다'는 minor를 지적한 것을 계약 작성 시 미리 반영한 것이다. 반면 채널당 광고 통화가 섞이는 경우(ad_performance에 한 채널이 여러 통화로 기록되는 극단 상황)는 계약이 의도적으로 범위 밖으로 뒀는데, 07 내장 리뷰가 이를 다시 지적했다 — 계약의 그 결정 자체는 유효하지만(FR-023 입력 경로가 아직 없어 실무상 발생 불가), 문서화가 계약 파일에만 있고 코드 주석에는 요약이 부족했다.

### 05 리뷰 범위가 적절했는가

05는 diff가 인라인 상한을 넘어 파일 경로 전달로 4개 관점(gen·data·arch·test)이 병렬로 돌았다. gen·data·arch는 지적 0건, test만 major 1(필터 인자 미검증)·minor 1(0 경계 미검증)을 냈다. 데이터 계층·구조 관점에서 지적이 없었던 것은 이 기능이 순수 읽기 전용이라 상태 전이·트랜잭션·마이그레이션처럼 그 두 리뷰어가 보는 위험 표면 자체가 거의 없었기 때문으로 보이고, 실제로 위험은 대부분 '인가 게이팅'(xv가 잡음)과 '테스트가 진짜로 잠그는가'(test 리뷰어가 잡음)에 몰려 있었다.
