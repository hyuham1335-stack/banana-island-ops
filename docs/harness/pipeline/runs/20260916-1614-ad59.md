## 서술

### 문제

요청 원문("must 다음 작업 확인 후 진행해줘")이 범위를 지정하지 않아 00-triage가 unclear로 판정했다. 세션 중 사용자가 FR-007(재생성+지시문)을 명시적으로 선택했다. 계획·구현 과정에서 여러 라운드의 지적이 나왔다: 01-plan 1라운드에서 critical 1건(content_history 이력을 UPDATE 이전에 쓰는 순서 오류)·major 3건, 02-cross-verify(외부 Gemini)에서 critical 1건(트랜잭션 부재 지적, 기각)·major 1건(versionNo TOCTOU, 수용), 05 code-review에서 major 3건(그중 2건이 같은 근본 원인 — resolveContentLink 호출 시점), 07 code-review(medium)에서 05가 놓친 진짜 동시성 버그 1건(submit과 regenerate 경합)과 minor 2건.

### 원인

1) 계약 작성 시 API_SPEC.md의 `{id}` 표기를 그대로 옮겨 적어 entrypoint_resolver(Next.js 파일 규약 `[id]`)와 어긋났다 — 표기 관습 차이를 계약-대조가 실행되기 전까지 몰랐다. 2) FR-007이 도입한 regenerateContentBody는 body를 바꾸되 status는 그대로 두는 첫 번째 액션인데, 기존 transition()::submit의 낙관적 잠금은 'status가 실제로 바뀐다'는 전제(다른 모든 액션이 지금까지 만족해온)에 기대어 status만 가드했다 — 이 전제가 깨지는 것을 계약·05 리뷰 모두 놓쳤고, 07의 /code-review(코드베이스 전체를 다시 훑는 별도 시각)가 처음 잡았다.

### 해결

계약을 실제 코드 규약에 맞게 수정(entrypoint `[id]`, 유닛 백틱 형식)했고, 01의 critical(저장 순서), 05의 major 3건(resolveContentLink 호출 시점을 UPDATE 이전으로, 상태 가드를 TRANSITIONS.submit.from 재사용으로)을 수리 후 델타 재리뷰(gen)로 수렴시켰다. 07에서 발견된 동시성 버그는 content-workflow.ts::transition()의 submit UPDATE 가드에 regenCount를 추가해 해결하고, 빈 문자열 instruction 처리도 함께 고쳐 같은 커밋으로 push했다. 코드 중복(major 아님, minor) 1건은 정확성 문제가 아니라 판단해 이번 PR에서는 반영하지 않고 deferred로 남겼다.

### 배운 점

새 서비스 함수가 '상태를 바꾸지 않는 채로 다른 필드를 바꾸는' 첫 액션일 때는, 그 필드를 참조하는 기존 액션들의 낙관적 잠금 가드가 여전히 안전한지 계약 단계에서 명시적으로 점검해야 한다 — 05 리뷰 지시에 '새 코드 자체'만이 아니라 '기존 코드와의 상호작용'을 넣지 않으면 각 리뷰어가 diff 안에서만 보게 되어 이런 경계 버그를 놓친다.

### 계약이 어디서 부족했는가

계약이 entrypoint 표기(API_SPEC의 `{id}` vs Next.js 파일 규약 `[id]`)를 처음에 혼용해 contract-trace critical 1건을 냈다(계약만 고쳐서 해결, 코드는 처음부터 맞았다). 더 크게는, 계약이 regenerateContentBody의 '상태를 안 바꾸는 body 변경'이 기존 submit()의 status-only 낙관적 잠금과 상호작용한다는 것을 명시하지 않았다 — 이것이 05가 아니라 07에서야 잡힌 근본 원인이다.

### 05 리뷰 범위가 적절했는가

05는 gen·data·sec·arch 4명이 라우팅됐고(test는 normal 프로파일 상한 4에 걸려 이번 라운드 제외) 각자 diff+계약만 보고 리뷰했다. 그중 gen과 data가 독립적으로 같은 근본 문제(resolveContentLink 호출 시점)를 다른 각도(CONTRACT_MISMATCH vs TX_BOUNDARY)로 잡아냈고, arch는 상태 가드 중복을 잡아냈다 — 이 부분은 05가 잘 작동했다. 다만 05는 diff 범위(변경된 파일)에만 집중해 diff 밖의 기존 파일(content-workflow.ts::transition())과의 상호작용은 누구의 체크리스트에도 명시적으로 없었다 — 07의 /code-review가 저장소를 더 넓게 훑어 이것을 잡았다. 다음부터는 '상태를 안 바꾸는 새 mutation'류 계약에는 05 리뷰 프롬프트에 관련 기존 가드 파일을 참고 대상으로 명시하는 것이 나을 것 같다.
