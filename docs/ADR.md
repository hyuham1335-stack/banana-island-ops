# 기술 결정 기록 (ADR)

> 결정 하나에 **결정 / 이유 / 트레이드오프 / 재검토 시점** 넷을 채운다. 트레이드오프가 빈 결정은 결정이 아니라 선호다.
> 새 의존성·프로바이더·인증은 여기에 ADR 을 먼저 쓴 뒤 도입한다 (`CLAUDE.md` 아키텍처 규칙).

## 철학

**검증한 것만 결정으로 굳힌다.** 실측 없는 상수를 상속하지 않는다. 아래 결정 대부분은 2026-09-13 에 「4일 안에 인터뷰용 MVP」라는 제약 아래 내렸고, 그 제약이 사라지면 재검토 시점이 온 것이다. 재검토 시점이 지난 결정을 근거로 새 코드를 쓰지 않는다.

## ADR-001: Next.js App Router 를 Vercel Hobby 에 올린다

- **결정.** Next.js(App Router, Node 런타임) 단일 리포. 페이지는 서버 컴포넌트, 쓰기는 Route Handler. 배포는 Vercel Hobby.
- **이유.** 사용자가 Vercel 을 정했고, 화면 9개 + API 를 4일 안에 내려면 프론트·백을 한 프레임워크에 두는 것이 가장 빠르다. 하네스 어댑터 `nextjs-ts` 가 이미 있어 `doctor`·게이트를 바로 쓴다.
- **트레이드오프.** Hobby 는 함수 상한 300초 고정, 크론 일 1회 정밀도, 상업적 사용 제한. 본문 생성을 한 요청에서 끝내야 하므로 큐·백그라운드 처리를 못 쓴다 → 라우트 `maxDuration` 60초 예산으로 강제. 서버 컴포넌트와 클라이언트 컴포넌트 경계를 잘못 그으면 DB 클라이언트가 번들에 들어간다 → `ARCHITECTURE.md` 금지 표.
- **재검토.** 인터뷰(2026-09-17) 후 운영 전환 시 Pro 여부. 본문 생성 p95 가 45초를 넘으면 스트리밍 또는 큐 검토.

## ADR-002: Drizzle ORM + Neon 서버리스 HTTP 드라이버

- **결정.** `drizzle-orm` + `@neondatabase/serverless` 의 HTTP 모드. 스키마는 `src/lib/db/schema.ts`, 마이그레이션은 `drizzle-kit generate` 로 `drizzle/` 에 SQL 로 남기고 로컬에서 적용.
- **이유.** 서버리스 함수는 연결 풀을 유지할 수 없어 HTTP 드라이버가 맞다. 스키마가 TS 라 계약의 「데이터 형태」와 같은 언어이고, 생성 클라이언트 단계가 없어 빌드가 가볍다. 사용자 선택.
- **트레이드오프.** HTTP 모드는 **다중 문 트랜잭션이 없다.** 상태 전이 + 이력 + 예시 등록이 부분 실패할 수 있다. 완화: 전이는 단일 `UPDATE … WHERE status = 현재상태`(낙관적 잠금)로 하고, 이력·예시는 그 뒤에 쓴다. 이력이 빠져도 상태는 맞다. 계획 상태는 파생이라(ADR-007) 두 행을 함께 바꿀 일이 없다.
- **재검토.** 부분 실패가 로그에 관측되면 해당 서비스만 WebSocket 드라이버(`Pool`)로 전환. 트래픽이 늘어 연결 수가 문제 되면 Neon 풀러 설정.

## ADR-003: Anthropic Claude 단일 프로바이더, `LlmClient` 인터페이스 뒤에

- **결정.** `@anthropic-ai/sdk` 하나. 모델 ID 는 `LLM_MODEL` 환경변수. 서비스는 `LlmClient { generateJson(system, user, schema, timeoutMs) }` 만 알고 구현체는 `lib/llm/client.ts`.
- **이유.** 사업계획서는 Claude/Gemini 를 병기했지만 4일 안에 둘을 검증할 수 없다. 사용자 선택. 인터페이스를 두면 두 번째 프로바이더는 구현체 하나 추가로 끝난다.
- **트레이드오프.** 프로바이더 장애 시 대체 경로가 없다 → `LLM_FAILED` 로 초안을 보존하고 재시도는 사람이. 모델별 프롬프트 최적화를 못 한다(하나뿐이라 필요도 없다).
- **재검토.** 콘텐츠 품질 비교가 필요해지거나 비용이 문제 되면 Gemini 구현체 추가(이 ADR 개정, `CLAUDE.md` 금지 목록 갱신).

## ADR-004: 인증 없음, 담당자/대표 역할 전환 쿠키

- **결정.** 로그인이 없다. 상단 역할 전환이 `role` 쿠키(`editor|admin`, httpOnly)를 세우고 서버가 매 요청 검사한다. `users` 테이블은 시드 2명으로 두고 역할별로 고정 매핑한다.
- **이유.** 사내 3명, 인터뷰까지 4일. 인증을 넣으면 반나절이 사라진다. 인가 규칙(admin 전용 동작)은 그대로 구현하므로 인증을 붙일 때 라우트는 안 바뀐다 — `getActor()` 의 구현만 바뀐다.
- **트레이드오프.** **누구나 쿠키를 바꿔 대표가 될 수 있다.** 사업계획서 3-3 「원가·재무 자료는 인가자만」을 기술적으로 보장하지 못한다. 배포 URL 을 외부에 알리지 않는 것으로만 막는다. 이것이 부채 #1 이다.
- **재검토.** 다음 중 먼저 오는 것: 배포 URL 외부 공개 · 인터뷰 종료 후 실운영 · 원가 데이터에 실제 값 입력. 그때 Auth.js(이메일+비밀번호, 초대제)로 `getActor()` 를 교체한다.

## ADR-005: 금액은 발생 통화로 저장하고 조회 시 환산한다

- **결정.** 모든 금액 컬럼은 `amount numeric(14,4)` + `currency char(3)`. 원화 환산 컬럼은 만들지 않는다. 환산은 서비스가 `fx_rates` 를 날짜로 조인해 계산하고, 결과 스냅샷이 필요한 곳(`cost_calc_results`)만 적용 환율을 함께 저장한다.
- **이유.** ERD 원칙 1. 환율이 매일 바뀌므로 환산값을 저장하면 「언제 환율」인지가 사라지고 과거 결과가 재현되지 않는다. 원가 시뮬레이션(슬라이더)은 같은 원가 행을 다른 환율로 보는 것이라 저장값이 없어야 성립한다.
- **트레이드오프.** 조회마다 조인·곱셈. 사내 규모에서는 무시할 수준. 환율이 없는 날은 조회가 실패할 수 있다 → `getFx` 가 그 이하 최신 행을 돌려주고 `staleDays` 를 표시한다.
- **재검토.** 정산일 환율(ERD 원칙 12 의 제외 항목)이 필요해지면 `fx_rates` 에 `kind` 를 더한다. 저장 정책은 바꾸지 않는다.

## ADR-006: 발행 계획은 구글 시트가 원본이고 단방향 pull 이다

- **결정.** `publish_plans` 는 Sheets API(서비스 계정, 읽기 전용)로 읽어 `sheet_row_key` 기준 upsert 한다. 시스템은 계획을 만들거나 고치지 않는다. 사라진 행은 지우지 않고 `on_hold`. Apps Script 푸시(Should)는 같은 동기화 함수를 부르는 웹훅일 뿐이다.
- **이유.** 팀이 이미 시트로 캘린더를 운영한다(사업계획서). 원본을 한 곳에만 두어야 양쪽이 어긋나지 않는다. 메모의 「한 글자 고칠 때마다 호출되면 안 된다」는 Apps Script 쪽 디바운스로 풀고 서버는 멱등(upsert)이라 여러 번 불려도 안전하다. 사용자 선택(읽기만).
- **트레이드오프.** 시스템 안에서 계획을 못 고친다 — 목업도 그렇게 설계됐다(「계획은 시트에서만 수정」). 즉석 콘텐츠는 계획 없이 존재하고 캘린더에는 나타나지 않는다. 서비스 계정 발급이 안 되면 CSV 업로드로 대체해야 한다(PRD Q3).
- **재검토.** 양방향이 필요하다는 요구가 실제로 나올 때. 그 전에는 열지 않는다.

## ADR-007: 계획과 콘텐츠는 1:1, 계획 상태는 저장하지 않고 파생한다

- **결정.** `contents.publish_plan_id` UNIQUE(NULL 허용). 계획 상태 컬럼은 없고 `derivePlanStatus(plan, content)` 가 계산한다. 재생성·반려 수정은 같은 콘텐츠 행을 갱신하고 이전 본문은 `content_history` 에, 발행 후 다시 만드는 것은 새 행(`source_content_id`)이고 계획 연결을 옮긴다.
- **이유.** ERD 원칙 9·10. 상태를 두 테이블에 두면 반드시 어긋난다. 파생이면 트랜잭션 없이도(ADR-002) 일관된다.
- **트레이드오프.** 계획 목록 조회가 항상 콘텐츠를 조인한다(사내 규모에서 무시). 「한 계획에 여러 콘텐츠」가 필요하면 스키마를 바꿔야 한다 — 현재 워크플로우에는 그런 경우가 없다.
- **재검토.** A/B 로 한 계획에 두 본문을 동시에 돌리자는 요구가 오면.

## ADR-008: 하드 룰은 코드가 검증하고 소프트 룰은 사람이 검수한다

- **결정.** 금칙어·필수표현(하드)은 프롬프트에 넣고 **생성 후 정규식 검증기**가 다시 검사한다. 차단 등급은 대체 표현 피드백으로 자동 재생성 1회, 잔존 시 검수 요청 불가(422). 경고 등급·필수표현 누락은 하이라이트만. 톤·형식·타깃(소프트)은 프롬프트에만 넣고 대표가 검수한다.
- **이유.** 메모: 「프롬프트에 넣어도 항상 보장되지 않는다. 기계적 검사가 필요. 톤은 사람이 검증.」 ERD 원칙 7. 사업계획서의 식약처·FDA 규제 준수와 Human-in-the-loop 가 이 구조다.
- **트레이드오프.** 정규식은 어간 변형·띄어쓰기를 놓친다(부채 #7). 자동 재생성 1회는 LLM 호출을 최대 2배로 늘린다 → 가드레일 「콘텐츠당 ≤ 8회」와 `regen_count` 로 관측. 차단 규칙이 지나치게 넓으면 정상 문장도 막는다 → 규칙에 `alternative`·`reason` 을 필수로 두어 담당자가 고칠 수 있게.
- **재검토.** 반려 사유 원장에 「검증기가 놓쳤다」가 3회 쌓이면 `detect_pattern` 보강 또는 LLM 기반 2차 검사 검토.

## ADR-009: 발행은 수동이고 URL 은 HEAD 로 존재만 확인한다

- **결정.** 어떤 채널도 자동으로 올리지 않는다. 담당자가 채널 형식으로 변환된 본문을 복사해 직접 올리고 「발행 완료」를 누른다. URL 은 선택 입력이고 HEAD 5초로 `ok|unreachable` 만 기록하며 실패가 발행 완료를 막지 않는다.
- **이유.** ERD 원칙 11, 사업계획서 「AI 초안의 즉시 자동 발행 금지」. 네이버 블로그·인스타·아마존은 글쓰기 API 가 없거나 제한적이고, Shopify 만 가능하다 — 하나를 위해 발행 계층을 만들 시간이 없다. HEAD 만 하는 것은 남의 사이트 본문을 읽지 않기 위해서다.
- **트레이드오프.** 발행 여부를 시스템이 보증하지 못한다(사람이 눌렀다는 기록뿐). 발행 글 내용 일치 검증은 없다(ERD 원칙 12 의 제외).
- **재검토.** Shopify Admin API 토큰이 준비되고 발행 건수가 월 15건을 넘으면 `publish_method='api'` 채널부터 자동 발행(US-034).

## ADR-010: 환율은 Frankfurter(ECB) 일 1회 크론, 수동 입력 폴백

- **결정.** Vercel Cron 이 매일 00:10 UTC 에 `/api/fx/refresh` 를 부르고 Frankfurter `latest?from=USD&to=KRW,PHP` 로 USD→KRW, PHP→KRW(=USD→KRW ÷ USD→PHP) 2행을 저장한다. 실패 시 전일 값 유지 + `staleDays` 경고, 대표가 수동 입력(`source='manual'`).
- **이유.** 키·계정이 필요 없고 세 통화를 다 지원한다. 메모 「매일 시작할 때 한 번 환율 저장」. Hobby 크론은 일 1회가 상한이라 정확히 맞는다.
- **트레이드오프.** ECB 참조 환율은 은행 매매 기준율과 다르고 주말·공휴일에 갱신되지 않는다(그날은 전일 값). 원가 계산 정밀도보다 「환율이 오르면 마진이 얼마나 줄어드나」를 보는 용도이므로 감수한다. 크론 라우트가 공개 URL 이라 `CRON_SECRET` 검사가 필수다.
- **재검토.** 실제 정산 환율이 필요해지면 한국수출입은행 API 등으로 교체(구현체만, `FxClient` 인터페이스 유지) 또는 정산일 환율 `kind` 추가.

## ADR-011: 판매 채널과 발행 채널을 `sales_channels.kind` 로 한 테이블에 둔다

- **결정.** ERD 의 `판매채널` 에 `kind enum('sales','content')` 를 더해 판매 채널 6개(광고·원가가 참조)와 발행 채널 4개(네이버 블로그·인스타그램·Shopify 블로그·Amazon 상세 — 규칙·계획·콘텐츠가 참조)를 한 테이블에 둔다. 채널 속성(`utm_source`·`utm_medium`·`link_policy`·`write_url`·`persona`·`tone`·`format`)도 컬럼으로.
- **이유.** 목업은 두 종류를 다른 객체(`channels`·`CH`)로 들고 있지만 ERD 는 하나뿐이다. 테이블을 둘로 나누면 `brand_rules.channel_id`·`brand_examples.channel_id` 가 어느 쪽을 가리키는지 모호해진다. 목업의 `CH` 속성은 규칙 테이블(`scope='channel'`)로도 표현 가능하지만, 시드를 두 곳에 나누면 4일 안에 관리가 어렵다 → 채널 컬럼을 기본값으로 쓰고 규칙이 덮어쓴다.
- **트레이드오프.** `kind='content'` 행에는 수수료율·유통경로가 의미 없다(NULL). 「Amazon US」(판매)와 「Amazon 상세」(발행)가 두 행이다 — 광고 성과와 콘텐츠를 잇는 것은 `ad_performance.content_id` 로 충분하다.
- **재검토.** 채널이 15개를 넘거나 발행 채널에만 있는 속성이 5개를 넘으면 분리.

## ADR-012: DB·코드 식별자는 영문 snake_case, ERD 한글명은 매핑표로

- **결정.** 테이블·컬럼·enum 값·TS 심볼은 영문. 한글 ERD 이름과의 대응은 `TRD.md` §4 표가 단일 출처. 화면 문구는 한글.
- **이유.** Drizzle·Postgres·계약 추적(`contract-trace` 의 심볼 grep)이 한글 식별자에서 불안정하고, 따옴표 없는 한글 컬럼은 SQL 에서 매번 인용해야 한다.
- **트레이드오프.** ERD 와 코드를 나란히 읽을 때 매핑표를 거친다. 상태값 번역(`검수대기=in_review`)이 화면 문구 사전(`lib/labels.ts`)을 하나 더 만든다.
- **재검토.** 없음. 되돌릴 이유가 생기지 않는다.

## ADR-013: UI 는 목업 토큰을 CSS Modules 로 이식하고, 테스트는 Vitest 만 쓴다

- **결정.** 목업 `bananaislandops_2.html` 의 `:root` 토큰·컴포넌트 CSS 를 `globals.css` + CSS Modules 로 옮긴다. Tailwind·UI 킷·상태 관리 라이브러리를 넣지 않는다. 테스트는 Vitest(순수 함수 골든 + 서비스 모킹 + 라우트 직접 호출), Playwright E2E 는 없다.
- **이유.** 목업이 이미 완성된 디자인이라 옮기는 것이 새로 짜는 것보다 빠르다(`UI_GUIDE.md`). 의존성이 적을수록 `npm audit` 게이트와 빌드가 조용하다. E2E 는 4일 안에 안정화할 수 없고 어댑터도 `e2e: null` 로 「없음」을 정직하게 기록한다.
- **트레이드오프.** 화면 회귀를 기계가 못 잡는다 → 인터뷰 시연 시나리오(PRD §7)를 손으로 1회. CSS Modules 는 클래스 재사용이 덜 유연하다 — 컴포넌트 수가 적어 문제 없다.
- **재검토.** 화면이 15개를 넘거나 두 번째 개발자가 합류하면 Playwright 스모크 3개 추가. Tailwind 는 넣지 않는다.
